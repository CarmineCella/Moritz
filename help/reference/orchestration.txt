# Orchestration: assisted orchestration, after Orchidea, on Musil's engine

@ orchestra
syntax: orchestra name [database]
A database of instrumental samples and the players who play it, shared by
name with orchidea. The database is a feature file in the layout of the
*SOL databases (Ircam's TinySOL, OrchideaSOL, FullSOL, or the MicroSOL
that comes with Moritz: microsol/microsol.spectrum.db), as Musil's db-load
reads it: the first line says the features (type, block, hop, number of
coefficients), then a line per sound, its path and its features; the names
of the files carry instrument, technique, pitch and dynamics
(Vn-ord-D#5-mf.wav). The sounds are found in the folder next to the file
that holds them, whatever it is called. Reading runs as a background job;
when it is done, the number of sounds and the players come out.

The database can be named instead of given as a file: orchestra band
fullsol, read tinysol, read microsol. A name is found as Musil's (dataset
name) finds it, in one place both share: a file registered under that name
(FullSOL, where you keep it: Extras > Datasets..., Register a file), then
the datasets folder (Settings, or Extras > Datasets...; by default
~/Documents/Moritz/datasets, where Download TinySOL puts TinySOL), then the
MicroSOL that comes with Moritz. The name of X.spectrum.db is x, without a
trailing year: FullSOL2020.spectrum.db is fullsol.

analyse makes a database out of a folder of sounds named as in the *SOL
databases (Orchidea's dbgen, the analysis of Musil's db-gen): every WAV
under the folder, its features in folder.spectrum.db next to the folder
(never over a file already there), which is then read. The Datasets window
does the same and registers the file by a name (Analyse a folder...).

Without players, the orchestra is Orchidea's default (two of each wind and
brass, a bass tuba, two of each string), of what the database has. A
player is an instrument code as the database names it (Fl, Ob, ClBb, Bn,
Hn, TpC, Tbn, BTb, Vn, Va, Vc, Cb...); Fl|Picc is one player who doubles.
Right-click the box for Info.

See the examples in examples/13-orchestration: sound-space (players,
doublings, range, techniques, dynamics) and, for what orchidea does with the
orchestra, static-dynamic, connections, memory, search and output.
arg name: the name orchidea uses (required)
arg database: a feature file, or a dataset's name (fullsol, tinysol, microsol), to read when the box is made (none)
msg read file: reads a database (a background job): a feature file, or a dataset's name (read fullsol); the sounds are looked for next to it
msg analyse folder [type block hop ncoeff]: analyses every WAV under the folder into folder.spectrum.db next to it, when the patch may write there (its folder, ~/Documents/Moritz; the Datasets window analyses a folder anywhere) (a background job; spectrum 2048 256 1024 by default; logspec, specpeaks, specenv, mfcc 13, moments 4), then reads it
msg players instrument [n] ...: the players, an instrument a player, a number after one making it that many players (players Vn 4 Va 2 Vc 2 Fl); A|B is one player who doubles, playing either (Fl|Picc); no instrument: the default orchestra
msg add instrument [n]: more players of an instrument
msg remove instrument: every player of an instrument
msg range instrument lo hi: only the instrument's sounds from lo to hi enter the search (pitch names, G3, or MIDI numbers, both included); range instrument: its whole range again
msg techniques name ...: only sounds of these techniques (ord, pizz-lv..., as the file names say them) enter the search, for every instrument; techniques alone: every technique
msg dynamics name ...: only sounds of these dynamics (pp, mf...) enter the search; dynamics alone: every dynamics. A segment a filter leaves no sound (nor a pitch of its partials) is a rest: orchidea says so, its report line says why, and the other segments are orchestrated
msg info: prints the database (sounds, instruments, their ranges and techniques) and the players in the Console
msg stop: cancels the reading
see: orchidea buffer~

@ orchidea
syntax: orchidea orchestra
Assisted orchestration, after Orchidea (Cella, Esling): a target sound in a
buffer~ imitated by the players of an orchestra object. The target is cut
into segments (one for a static target, or at its onsets), each analysed
into the database's features and into the pitches of its partials; for
each segment a genetic search finds the combinations of sounds, one per
player or a rest, whose summed spectrum is nearest the target's, with an
asymmetric distance (a partial the target lacks costs more than one it has
and the solution lacks). The search runs as a background job, on Musil's
engine: Musil's orchestrate-mimetic with the same target, database,
orchestra and seed finds the same notes, on every system.

When it is done, the solution comes out as one message a note: its number
(from 1), instrument, pitch, dynamics, technique, onset and duration (ms),
the sound's path, the cents the target's partial is away from the pitch,
and the player (from 0), then the done outlet bangs (not after a run that
failed with a message); a note the target holds across segments on the
same player is one longer note. The distance (the mean cost of the chosen
solutions) comes out on its outlet, and the solution as a score on the last
(score token, for a score object: a row an instrument in orchestral order, a
note a sound chosen, with its dynamics, technique, cents and place, and its
sample as its sound, so the score object plays it and its roll edits it). With
an out buffer~, the chosen
samples are summed into it in stereo, the players seated as in Orchidea's
mixes, so that the orchestration is heard at once (scaled down when it
would clip). The ten best solutions of each segment are kept, each sounding something
else (two players of an instrument with their sounds swapped are one
solution): choose puts another in place, show lists them, report says what
each segment found. A segment where no sound passes the filters is a rest.
Right-click the box for Report and Save the solution...

A dynamic segmentation (flux or frames) uses Musil's dynamic settings, those
of dynamic_orchidea.mu, for every setting no message has set: population 500,
epochs 500, sparsity 0.01, partials 0.3 (0 when the database is tiny, as
MicroSOL), solutions 5, sustain 1, hold 4000 ms, dovetail 0.75 (pivot notes),
connection path (the least melodic movement). A static target (segmentation
none) keeps the defaults below. report prints the settings a search ran with.

See the examples in examples/13-orchestration, one a feature: static-dynamic
(segmentation none, flux, frames, onsets), connections (closest, best, path),
memory (sustain, hold, dovetail, hysteresis), search (population, epochs,
sparsity, seed, show, choose), sound-space (the orchestra's players and
filters), output (score, notes, write, roll), and orchidea (four targets, a
piano phrase orchestrated dynamically).

A search of 300 individuals over 300 epochs on TinySOL takes well under a
second for a static target; a segmented target takes that per segment.
arg orchestra: the name of an orchestra object
msg run target [out]: orchestrates the buffer~ target (mixed to mono); the sum of the chosen samples goes to the buffer~ out
msg population n: individuals of the genetic search, the combinations tried at each generation, 2 to 20000 (300; 500 when dynamic): more, nearer the target and slower
msg epochs n: generations at most, 1 to 100000 (300; 500 when dynamic)
msg patience n: generations without a better population before a search stops (150)
msg sparsity x: how often a player is left out of a solution, 0 to 1 (0.001; 0.01 when dynamic; 0.1 for a single instrument as target): more, fewer players
msg seed n: the random seed: the same seed gives the same orchestration (1)
msg pursuit k: 0, a random first population; k, the first population drawn from the k sounds nearest the target per player (0)
msg crossover x: the crossover rate (0.8)
msg mutation x: the mutation rate (0.01)
msg positive x: the cost of a partial the solution has and the target lacks (0.5)
msg negative x: the cost of a partial the target has and the solution lacks (10)
msg regularization x: above 0, solutions with fewer players are preferred (0)
msg segmentation none | flux | frames: none, one segment (a static target, the default); flux, at the peaks of the spectral flux above threshold, timegate apart; frames, every block of the database
msg onsets ms ...: the segments start at these times instead
msg threshold x: the flux's peaks above this share of its largest count as onsets (2: none does)
msg timegate ms: onsets at least this far apart (100)
msg partials x: the target's partials above this share of the strongest give the pitches the sounds must have, 0 to 1 (0.2; 0.3 when dynamic, 0 with a tiny database); 0, no pitch filter: every sound may serve (noisy targets, MicroSOL)
msg window n: the window the partials are read with, a power of two (32768: large for a low target)
msg pitches name ...: pitches every segment admits besides its partials'
msg octaves n ...: the pitch filter widened by octaves (octaves 0 -1: the partials' pitches and the octave below)
msg connection closest | best | path: how a solution is chosen per segment among the ones kept: closest to the one before in timbre (Orchidea's), the best of each alone, or the sequence with the least melodic movement (closest; path when dynamic). With path and sustain, each solution of a segment offers its continuation into the next (the next segment's best with those players holding their sound), which the path takes where holding costs little
msg solutions n: the best solutions kept per segment, among which the connection and choose pick (10; 5 when dynamic)
msg hysteresis x: above 0, each segment leans in timbre towards the solutions chosen before: a timbre memory, an even colour (0)
msg dovetail x: above 0, a solution that drops the pitches of the one before costs more: pivot notes between chords (0; 0.75 when dynamic)
msg movement x: for connection path, the cost of a semitone a player moves (1)
msg sustain 1/0: 1, a player whose pitch the target keeps holds its sound on into the next segment, one longer note, not searched again (1); with connection path, which is chosen once every segment is searched, each solution offers instead its continuation into the next segment, among that segment's solutions. Without a pitch filter (partials 0) the target keeps every pitch: a player holds until hold
msg hold ms: a held note is never longer than this; the player starts it again (no limit; 4000 when dynamic); hold alone: no limit
msg seating 1/0: 1, the mix seats the players as Orchidea's mixes do (violins left, cellos right); 0, all in the middle (1)
msg choose segment n: solution n (from 1, best first) of a segment (from 1) in place of the one chosen: the notes and the mix again
msg notes: the notes again
msg score: the solution as a score again (score token, out of the last outlet)
msg show segment: prints the solutions of a segment with their costs and sounds (the chosen one starred)
msg report: prints a line per segment: its cost, players, players holding on (the notes the chosen connection holds from the segment before: one longer note each), sounds in the search space, and the target's pitches no instrument of the orchestra has; a rest says why
msg write file: saves the notes as an Orchidea connection file (Musil's score-load reads it), in the patch's folder or in ~/Documents/Moritz (elsewhere: not written; its menu's Save... writes where you choose)
msg roll buffer: writes the notes into a buffer~, a frame a note: onset (s), pitch (MIDI, with its cents), player, duration (s); plot in scatter mode draws it as a roll, a colour a player
msg stop: cancels the search
see: orchestra score buffer~ play~ code
